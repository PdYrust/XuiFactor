# XuiFactor v0.6.0

## Highlights

- Stable release for 3x-ui 3.x (tested against 3.10.2). Clients are identified by email as in the panel, and inbound scoped commands resolve membership through the panel `clients` and `client_inbounds` tables.
- PostgreSQL backend next to SQLite. A panel running PostgreSQL is detected the same way the panel decides: `XUI_DB_TYPE` selects it and `XUI_DB_DSN` supplies the connection, read from the environment or the panel service environment file. `database_backend` and `database_dsn` configure it explicitly.
- Master and node panels. Install XuiFactor on the master: it factors local traffic and the node traffic the master merges, exactly once. On a panel managed by a master, ticks are refused so node traffic is never factored twice.
- PostgreSQL ticks never wait for a row the panel is writing, so they cannot deadlock with the panel's traffic jobs. Such a client is reported as `deferred` and the next tick factors its full delta.
- `doctor` reports the database backend and the panel role; `backup` uses `pg_dump` on PostgreSQL; read-only commands open PostgreSQL in a read-only session.

## Package Names

```text
xui-factor_v0.6.0_linux_amd64.tar.gz
xui-factor_v0.6.0_linux_arm64.tar.gz
```

Use the archive that matches the server architecture.

## Install

```sh
tar -xzf xui-factor_v0.6.0_linux_amd64.tar.gz
cd xui-factor_v0.6.0_linux_amd64
sudo ./scripts/install.sh
```

Use `scripts/update.sh` from the extracted package when upgrading an existing installation. On systemd hosts, install enables and starts `xui-factor.service` by default, and update enables and restarts it by default.

## Upgrade from v0.4.0

v0.4.0 runs on 3x-ui 2.x; this release requires 3x-ui 3.x. Upgrade the panel first:

1. Stop `xui-factor.service`.
2. Upgrade 3x-ui and let the panel boot once so its database migration completes.
3. Install this release with `sudo ./scripts/update.sh`.
4. Run `xui-factor doctor`, then `xui-factor reconcile --dry-run` and `xui-factor reconcile`.

The metadata migration drops baseline columns tied to the removed `client_traffics.all_time` counter, keeps one active exclude and override per client, and sets metadata schema version 3. It does not modify traffic counters. A panel database that still has `client_traffics.all_time` is rejected with an upgrade hint.

## Upgrade from v0.5.0-beta

- No metadata migration and no reconcile run are needed. `sudo ./scripts/update.sh` replaces the binary and the service unit and restarts the service.
- If XuiFactor runs on a node, its ticks stop after the upgrade. Uninstall it there with `sudo ./scripts/uninstall.sh` and install it on the master. Factors already applied on the node stay in its counters and the master's.
- Auto backend detection no longer selects PostgreSQL from a leftover `XUI_DB_DSN` alone; check that `doctor` reports the expected `backend`.

## Operator Checks

After installing or upgrading, run:

```sh
xui-factor doctor
xui-factor status
xui-factor report
xui-factor reconcile --dry-run
xui-factor cleanup --dry-run
```

`doctor` should report `backend: sqlite` or `backend: postgres` to match the panel, and `role: standalone` or `role: master`. Use `systemctl status xui-factor.service --no-pager` to confirm daemon state on systemd hosts.

If `/etc/xui-factor/config.json` contains a `database_dsn` with a password, restrict it with `sudo chmod 600 /etc/xui-factor/config.json`. New installs create the file with that mode.

## PostgreSQL

Set the backend in `/etc/xui-factor/config.json` only when automatic detection does not apply:

```json
{
  "database_backend": "postgres",
  "database_dsn": "postgres://x-ui:password@127.0.0.1:5432/x-ui?sslmode=disable"
}
```

Commands print the DSN with the password redacted. `xui-factor backup` requires `pg_dump` and writes `.dump` files that restore with `pg_restore`.

## Master and Node Panels

The master adds each node's counter deltas to its own client rows and pushes the combined usage back to its nodes, which enforce quotas with it. XuiFactor on the master therefore factors node traffic once, and nodes enforce quotas with the factored totals. A panel counts as a managed node when a master pushed client usage to it within the last 24 hours; there, ticks are refused and `doctor` reports `role: node`. Set `"factor_on_managed_node": true` on a node only to factor that node's traffic alone, with the master not factoring the same clients.

## Policy Model

XuiFactor resolves one effective decision per client:

```text
exclude > override > single-user rule > inbound scope > global scope
```

Disabling rules or removing policies does not revert previously factored traffic. Removing an exclude or override resumes future matching from current counters and does not retroactively factor earlier traffic.

## Behavior Notes

- A client has one traffic row per email; factors apply across every inbound it is attached to, and it belongs to the first active rule or scope that enrolls it.
- A client deleted and recreated under the same email gets a new traffic row; reconcile and the next tick move its rules, excludes, and overrides onto that row.
- Renaming a client in the panel keeps its traffic row but changes the email, and XuiFactor treats the result as a different client. Re-issue excludes and overrides for the new email.
- `traffic_applied` audit events record `extra_up` and `extra_down`; report traffic impact sums both.

## Safety

- XuiFactor does not modify 3x-ui source code.
- XuiFactor metadata lives in `xui_factor_*` tables.
- Read-only commands such as `status`, `explain`, `report`, `audit`, `excludes`, and `overrides` do not modify traffic counters.
- Migrations, reconcile, and cleanup touch only XuiFactor metadata and never subtract previously factored traffic.
- Installer and uninstall scripts preserve `/etc/x-ui/x-ui.db` and do not touch a PostgreSQL panel database.
- Builds require Go 1.25 or newer.
